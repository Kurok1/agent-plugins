# TypeScript 项目范式

采用“包间明确依赖、包内按领域聚合”的布局，让修改同一功能时需要阅读的文件相邻。按项目规模裁剪；用户要求、仓库约定和框架必需的布局优先。

编写或修改实现、改变行为或审查代码时，读取[代码规范](references/code-conventions.md)，应用其中与本次任务有关的类型、输入边界、错误和异步规则。纯目录迁移保留已有实现，使用下文的迁移与验证流程。

## 确定组织层级

先查看当前任务涉及的入口、目录、导入关系、`package.json`、TypeScript 配置与现有验证命令。按职责和共同变更的关系分类，文件名前缀只作为线索。

- 单包项目：先在 `src/` 下划分领域模块。功能增加本身不构成拆 package 的理由。
- Workspace：包对应独立的依赖、复用、运行环境或发布边界；包内仍按领域分目录。已有包边界合理时，整理其内部即可。
- 新增功能：优先进入所属领域，只为具有独立职责的一组代码建立子目录。局部任务沿用周边结构，全仓迁移须属于用户任务范围。
- 框架项目：保留路由、组件、构建插件等约定入口，在其允许的位置组织领域代码；不要求改变框架或模块解析方式。

## 包内按领域聚合

推荐的模块形状，按实际职责选取文件：

```text
src/
  index.ts
  orders/
    order-types.ts
    order-codec.ts
    order-validation.ts
    order-workflow.ts
  payments/
    ...
tests/
  orders/
    ...
```

领域可以是订单、会话，也可以是认证、Git、MCP、压缩等独立能力。基础设施包可按具体实现分组，如 `memory/`、`sqlite/`；界面按功能组织组件、状态、hooks 与展示辅助函数。

- 独立的领域模型、解析与序列化、校验、执行流程分文件，放在同一领域目录。流程文件导入这些能力，聚焦执行顺序和状态转移；组件局部类型沿用项目风格。
- 根目录主要保留公共入口、整体装配以及真正跨领域的少量定义。共享代码先确认所属职责，避免形成不断扩大的 `utils/`、`types/` 或 `helpers/` 杂物目录。
- 保持浅层目录；只有出现更细的独立功能簇时才继续拆分。示意中的文件和目录按需创建，不预建空壳。
- 命名表达职责，遵循已有大小写和后缀约定。目录迁移可保留文件名及文件头，减少与本次目标无关的变化。
- `index.ts` 用于有意设计的公共接口；内部模块优先直接导入实现文件，避免经由本包根入口形成循环。无需在每层补建 barrel。
- 测试沿用现有的相邻测试或集中 `tests/` 方式。较大的测试目录可按对应领域细分，夹具放在相关测试附近；小型测试目录可以保持平铺。

## 多包依赖与运行环境

新建 workspace 可用 `apps/` 放应用入口、`packages/` 放复用库；已有工作区命名保持原样。依据业务画出实际依赖图，方向通常是应用或装配层调用业务能力与适配器，后者依赖领域契约。核心业务通过端口使用外部能力，SDK 和平台细节由适配器承担。

- 包间通过声明的公开入口访问。将内部依赖写入 manifest；使用 TypeScript project references 时，使其与实际内部构建依赖保持一致。
- 防止循环依赖和跨包相对路径访问 `src/`；已有应用内部 alias 可以沿用，但不能借 alias 绕过包的公开边界。
- 组合第三方实现的职责放在装配入口，领域库不反向依赖应用。只有具备独立职责时才设立单独的装配包。
- 同时服务浏览器和 Node 的库，区分浏览器安全契约与 Node 实现，可采用根入口和 `/node` 子路径。浏览器可达的依赖图不引入 Node、数据库或仅服务端可用的实现；仅需要类型时使用 `import type`。
- ESM 导入遵循实际运行方式：Node 直接运行编译产物时使用能解析到产物的扩展名，常见为 `.js`；bundler 或框架项目保持其既有解析约定。

运行时、包管理器和版本以当前项目为准。这些原则不要求新增 monorepo、切换 ESM 或复制某个项目的包名与层数。

## 整理已有目录

先列出受影响文件的“原位置 → 目标领域”映射，再按领域迁移。未明确要求改变接口或行为时，保持公开模块路径、导出符号和业务语义一致。

1. 依据映射更新静态导入、导出、动态导入、类型导入、测试 mock 和夹具引用。区分模块路径、资源路径与普通字符串，只重写已确认的路径。
2. 核对 `import.meta.url`、`new URL()`、worker 和子进程入口、模板、proto、静态资源及打包配置；同时考虑源码位置和构建产物位置。
3. 更新指向移动文件的文档及已有代码索引；在既有约定文档中简要记录领域归属，避免重复维护多份架构规则。
4. 对照移动前后的内容审查，确认差异来自目录和引用调整；保留其他人的改动，将无关行为优化留在本次任务之外。

## 验证与交付

运行当前项目提供的边界检查、格式、lint、类型、构建与相关测试。纯目录迁移优先复用现有行为测试，不用只验证文件位置的测试代替运行验证。

迁移涉及输出路径时，先按项目清理命令移除已知构建产物，再重新构建，防止旧 `dist/` 掩盖错误；保留源文件、夹具和用户数据。对本次移动影响的资源加载或进程启动入口，确认其仍能从最终产物运行。

完成时说明领域划分、主要迁移、公共边界是否改变及验证结果。检查未完成时明确说明实际限制。
