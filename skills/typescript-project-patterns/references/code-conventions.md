# TypeScript 代码规范

应用与本次改动有关的规则，保留项目已有的框架、公共契约和工具链。格式、引号、分号与导入排序交给现有 formatter/linter，类型别名与 interface 的选择沿用模块风格。

## 类型与状态

- 新项目优先启用 `strict`；已有项目遵循当前 `tsconfig`，新增严格选项单独评估其影响，避免局部需求引发全仓修复。
- 外部或尚未验证的数据使用 `unknown`，通过缩窄获得领域类型。不要把 `any`、非空断言或双重断言作为解决类型错误的默认方式；必须断言时说明由何处保证不变量。
- 局部变量依赖推断，公开函数和跨模块契约明确输入与输出，防止实现细节意外变成 API。只导出消费者实际需要的符号。
- 用可辨识联合表达互斥状态，让各状态只携带有效字段；分支处理检查穷尽性，避免多个布尔值与可选字段组合出无效状态。
- 明确缺省、空值、零、空字符串与 `false` 的区别。合法的假值应被保留，缺省回退按语义选择 `??` 或显式判断。
- 共享输入和快照在合适处使用 `readonly`；它只提供编译期约束。跨信任边界需要运行时隔离时，明确复制或冻结策略，避免意外修改调用方数据。

## 输入与副作用边界

- HTTP、JSON、环境变量、文件及持久化记录在进入领域逻辑前解析和校验。TypeScript 类型断言不能代替运行时验证；复用项目现有校验工具，不为此规范单独增加依赖。
- 解析、规范化与业务验证的职责清晰：转换仅按已定义的输入协议执行，错误指出具体字段或路径。副作用开始前完成所需验证。
- 领域计算尽量保持纯函数；时间、随机数、网络和存储等影响结果的依赖在边界注入，按实际需要使用少量明确接口。
- 通过名称表达领域含义与单位，如 `timeoutMs`、`sizeBytes`。注释解释协议约束、业务原因和不能破坏的不变量。
- 抽象围绕已经存在的职责或复用需求，保持函数与模块的单一目的。仅有一次简单调用时，优先直接组合，避免引入通用框架和多层透传。

## 错误与诊断

- 区分预期业务失败、外部依赖故障和程序错误，沿用项目既有的异常或结果类型约定；同一接口的失败表达保持一致。
- 捕获异常要有明确用途：恢复、转译、补充上下文或清理。需要重新抛出时保留原始错误链；有意降级时定义诊断方式及返回语义。
- 错误关联稳定的操作身份和必要上下文；日志避免包含凭据与完整敏感载荷，对外错误与内部诊断分开。
- 取消按操作契约单独处理。重试仅用于已定义为可重试、且重做安全的操作，并限制次数或总时限；结果不明的写操作先核对状态。

## 异步与资源生命周期

- Promise 应被等待、返回给调用方，或交给有明确错误处理与关闭责任的后台任务管理者；单写 `void someAsync()` 不处理拒绝。
- 创建者负责释放连接、文件句柄、定时器和监听器，使用 `finally` 或项目已有的释放机制覆盖失败路径；借用者不关闭共享资源。
- 取消信号向底层操作传递，实际结束操作并等待必要的清理。用超时 Promise 结束等待，不等于已经取消底层任务。
- 有依赖顺序或共享状态写入的操作按契约串行，独立任务可并行。`Promise.all` 的首次拒绝不会停止其余任务，失败后的取消或收尾需要明确处理。
- 对工作区、会话或筛选条件切换等异步界面操作，使用身份、请求代次或取消机制，防止迟到结果覆盖当前状态。

## 测试与改动范围

- 验证可观察行为和契约；按实际变更覆盖正常路径、相关边界及失败清理。修复缺陷时，在合适层级保留能复现问题的回归用例。
- 测试替身放在外部能力边界，避免为私有实现细节编写脆弱断言；真实序列化、资源定位或进程交互需要对应集成验证时再加入。
- 修复类型或 lint 问题时优先修正模型与实现。确有工具限制才局部抑制并记录原因，保留其余检查。
- 遵循仓库现有测试门禁；纯搬迁和低影响机械修改复用已有测试，不为匹配实现文本或文件布局增加测试。
